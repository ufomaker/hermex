# Hermex 原生鸿蒙移植与验收方案

日期：2026年10月20日。目标设备：用户的 HarmonyOS 6 手机。实施：AntiGravity；监督、范围控制和独立验收：Codex。

## 交付目标

将开源 Hermex 移植为 ArkTS 和 ArkUI 原生鸿蒙应用，作为手机控制电脑上 Hermes 的日常入口。支持配置自己的服务器地址，使用国内可直连入口时手机无需翻墙。电脑保留执行环境、模型和文件。另验证 Hermes 调用 Codex 与 Antigravity 的真实任务链路，不把模型列表出现这些名字视为调用成功。

采用分阶段实现，但基本聊天原型不是最终交付。完整日用功能必须在功能对照中逐项关闭；仅平台独有功能采用鸿蒙等价能力。没有用户同意，不把未完成项改写成“不需要”。主界面、聊天、文件和任务管理不能用 WebView 套壳代替。网页登录授权页面可在系统浏览器中完成。

## 原生实现和协议边界

在 Fork 新建 `harmonyos/`，原 iOS 工程尽量保持原样，避免每次上游合并都产生界面冲突。鸿蒙端使用 Stage 模型，ArkUI页面、可观察状态、协议层、持久化及平台能力分别组织。不要为迁就手机新写一套 Agent，也不要把现有 Hermes 生产配置改成开发环境。

优先直连 Hermes Dashboard：REST负责状态、认证、历史和管理；ticket鉴权的 WebSocket JSON RPC 负责实时会话和控制。不能把 legacy webui 的 SSE 协议与直连 Hermes 的 WebSocket 混成一个接口。legacy模式使用独立适配器，沿用已配置服务时必须清晰区分。

实现者首先阅读并校验这些来源：

- `HermesMobile/Networking/Hermes/HermesConnection.swift`：认证、Cookie、原生token、401恢复和跨域防护。
- `HermesGateway.swift`：ticket、gateway.ready、client.capabilities、心跳、多调用复用和连接代次。
- `HermesCall.swift`、`HermesREST.swift`、`HermesCompatibility.swift`：方法、参数、版本兼容和写入边界。
- `HermesMobile/Networking/Bots/`、`Features/Hermes/`：实时事件、Bot会话与显示；`Features/Chat/`及其他 Features：对应功能行为。
- `HermesMobile/Networking/Endpoints.swift`、`SSEClient.swift`和APIClient扩展：legacy适配。
- `HermesMobileTests/`及其fixture：跨平台语义回归，禁止机械照抄Swift语法。

所有路径、方法和字段来自固定版本源码或运行服务；建立协议对照表，记录来源、请求、响应、事件、错误和测试证据。不得猜造 `/chat` 等“看起来合理”的接口。会话存储ID、运行实例ID、profile和服务器身份分别建模。

持久化密钥用鸿蒙安全能力保护，不将密码/token写入普通偏好、源码、日志或Git。普通服务器列表、草稿和缓存与认证分离，并以服务器及profile隔离。TLS保持证书校验；重定向不能泄露鉴权头。断线恢复只补读或重连，发送结果未知时不得自动重发指令，避免重复执行。

AntiGravity须先在仓库建立细化的 `FEATURE_PARITY.md`，逐项标出上游位置、鸿蒙实现、构建和运行证据。下表全部纳入日用交付；支持取决于服务端能力的项目需保留清晰能力提示。

## 测试和交付证据

1. 可重复构建：记录DevEco/SDK/API、命令、代码提交、退出码及包的SHA256。ArkTS编译必须真实通过，不能用文本检查替代。
2. 协议回归：覆盖分包、中文UTF8、多事件、未知字段、RPC乱序、过期连接、401、断线与取消、写入结果未知及跨服务器隔离。模拟服务验证属于协议测试，不能计为真实Hermes验收。
3. 模拟器或设备UI：保存登录、会话、流式聊天、表格代码、审批、文件和错误恢复截图及运行日志；每个交互实际操作。
4. HarmonyOS6真机：安装、中文输入、前后台、锁屏后恢复、文件选择分享、权限拒绝及覆盖升级。签名、开发者账户和设备授权由用户在必要时完成。
5. 实际Hermes和跨Agent：使用隔离测试会话与目录，记录服务版本、脱敏请求ID、产物和执行归属；用户输入凭据，不抓取现有密钥规避授权。
6. 国内蜂窝网络：用户手机关闭代理后实测。没有这条证据不能声称已达到手机免翻墙使用。
7. 输出：完整Fork源码、签名HAP及校验、安装与启动指南、服务器连接说明、测试报告、逐项功能对照、已知限制和回滚方法。没有真机或外网证据时只能标记“实现完成，验收待办”。

## 上游新功能同步机制

保持 `upstream` 指向原作者、`origin` 指向用户Fork；master跟踪上游，鸿蒙开发在独立分支。不得强推或覆盖用户分支。新增 `UPSTREAM_BASELINE.md` 记录已合并iOS提交、已评估提交、鸿蒙适配提交和后端契约pin，这三种进度不能混为一谈。

每周检查一次上游新提交、Release、协议和功能目录变动。先形成变更清单，分类为新功能、修复、协议变更、iOS专属或依赖升级；每条关联鸿蒙代码、测试及状态。更新上游代码并不等于鸿蒙已得到新功能。协议/安全修复优先评估，普通新功能进入下一次同步批次，不能长期只更新README。

采用用户Fork内的本地分支和受审查提交集成；需要PR时仅向用户Fork提交，禁止向原作者仓库发消息或PR。依赖、签名、凭据和实机安装不自动升级。自动检查可生成清单，功能同步必须由AntiGravity实际实现并由Codex核验。维护目标是持续功能对齐，不是只复制上游源码。

## 协作和监督

AntiGravity承担工程、实现、构建、测试与缺陷修复；不得继续创建子Agent。优先已安装的 `agy` CLI和当前可用模型，避免改用户的全局模型设置。Codex只编写范围与移植文档、检查结果、组织验收，不承担应用实现代码。

每个阶段在 `docs/harmonyos/STATUS.md` 留下当前提交、真实构建命令和退出码、测试证据、未完成项和下一步；状态必须对应实际进程及文件。每次最终回复最多10条，避免贴长日志。Codex按阶段审查，未变化时保持安静；只有达到交付标准才通知完成，缺少必要人工输入时例外提出一个具体问题。
